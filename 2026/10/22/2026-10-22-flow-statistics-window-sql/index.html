8.7 秒到 231 毫秒：保留统计口径的 MySQL 窗口函数优化

发表于 2026-10-22 分类于 工程实践

有索引的统计 SQL 也可能很慢。这次优化把两次全历史最新状态判断合并为一次窗口计算，生产只读对比快约 37.6 倍；真正难的是保留重复键、空时间和跨天在场的原有口径。

先限定这次“快了 37.6 倍”的范围

人流量统计页面等待约 8 秒，浏览器内容下载却不到 1 毫秒。这个信号说明主要时间在服务端响应之前，但不能据此直接认定数据库就是唯一原因。

随后单独测量 SQL，发现两条全历史状态查询确实占了主要时间。在同一生产数据只读快照、固定统计时刻下，对比结果如下：

查询 耗时
旧在场及滞留统计 4605.58 ms
旧累计离场统计 4089.68 ms
旧两条合计 8695.26 ms
新合并统计 231.31 ms

约 37.6 倍是这组统计 SQL 的耗时对比，不是完整接口已从 8.7 秒降到 231 毫秒。原接口共有 5 条查询，改造后为 4 条；服务发布后仍要验证完整响应。


图 1：优化的核心是减少重复计算，不是给已有索引再起一个新名字。

索引已经存在，慢在哪里

现场 MySQL 为 8.0.27，流水表按通行时间做 RANGE 分区，共 97 个分区，元数据估算约 395 万行。已有人员、有效标记与时间相关索引，因此“缺人员索引”不是正确结论。

旧查询对每条候选流水做一次 NOT EXISTS 判断：同一人是否还有更晚的有效记录？如果没有，就把这条记录视为当前状态。在场统计做一遍，离场统计又做一遍。

下面是去掉业务过滤条件后的逻辑骨架。实际等价改写必须保证内外层使用原有的设备、有效状态及删除条件：

执行计划显示，最慢的两条查询涉及全部分区，反关联虽使用了索引，仍需反复定位和过滤。表已经分区不代表查询就能裁剪到当天；而业务本来要统计跨天仍在场的人，也不能为了裁剪，直接把候选数据限制成当天。

这是优化的第一条边界：查询慢可以改实现，统计口径不能顺手改掉。

一次排名，复用同一批最新状态

新实现对有效候选记录按人员分组，按时间、ID 倒序排名，再从最新记录同时聚合在场、离场和滞留分桶。

@as_of 要在对比前固定，例如 SET @as_of = '2026-10-22 17:00:00'。真实接口可使用当前时刻；新旧比较时不应让时间边界随两次查询漂移。

Service 从这次结果读取新增的内部离场聚合字段，去掉独立的离场查询调用。外部响应字段保持不变，本次也没有新增索引或表结构迁移。

最难的两处语义：并列记录与 NULL

为什么不用最常见的 ROW_NUMBER()？因为原表的 id 在整个分区表范围内不是单列唯一约束。原查询里，如果两条记录的时间和 ID 都相同，它们互相都不属于“更晚记录”，因此可能同时保留。

ROW_NUMBER() 会对并列行分别编号；DENSE_RANK() 则为同排序值的行赋予同一排名。这个差异见 MySQL 8.0 窗口函数说明。在此次兼容优化中，保留并列行才符合原口径。

空时间也不能丢。旧反关联中的时间比较遇到 NULL，不会得到 TRUE，因而这些记录可能全部通过 NOT EXISTS。只保留 latest_rank = 1 会漏掉某些空时间记录，所以新实现还显式保留 event_time IS NULL。


图 2：并列、空时间与跨天状态决定了优化是否等价，不能仅比较普通样本。

场景 必须保持的行为
同人、不同时间 按最新时间决定状态
同人、同时间、不同 ID 用 ID 决定先后
时间与 ID 都相同 保留原有并列记录
空时间 保留原 NULL 语义，进入未知时间分桶
昨天进场、今天没有流水 仍可能计入当前在场
恰好 12 / 24 小时 分别进入 [12,24)、[24,+∞)

因此，“在场人数”这个产品名称，在历史异常数据下可能仍体现记录计数语义。若要强制“一人一条”或治理空时间，应作为另一项业务调整，不能藏在性能优化里。

按原笔记，11 个相关测试通过，代码已推送并打包，但当时尚未发布服务。本篇整理没有重新运行生产查询，也没有把这组数字写成所有数据规模下的保证。

窗口函数不是天然比反关联快。它同样有排序和中间结果成本，数据分布改变后仍需看执行计划。这次有效，是因为它把两次重复的全历史最新状态判断合并成一次，并且用边界测试与同快照对比守住了原有统计语义。
