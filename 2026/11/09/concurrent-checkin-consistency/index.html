同秒签到冲突之后：用唯一键、事务和条件更新守住一致性

发表于 2026-11-09 分类于 工程实践

四个不同组长在同一秒签到，两人成功、两人失败；更麻烦的是，失败请求也留下了在岗记录，装备被占用却没有完整绑定。这不是一个“编号重复”就能概括的问题，而是业务编号、事务边界和状态竞争同时存在缺陷。修复也不只改一行编号生成代码，而是让整次签到真正做到唯一、原子、可回滚。

失败请求为什么留下了成功痕迹

原签到链路可以概括为三步：创建打卡记录、把装备改为已领用、写入装备绑定。绑定编号使用“B + yyyyMMddHHmmss + 请求内序号”，而每个请求的序号都从 1 开始。

两个请求只要落在同一秒，且各自生成第一条绑定，就会得到完全相同的编号。数据库上的 uk_eq_bind_sid 唯一约束正确拦截了重复数据，但前面的写入已经发生了：

  1. 打卡记录已经插入，所以失败请求仍可能显示为在岗；
  2. 装备状态已经更新，所以装备仍显示为已领用；
  3. 后续绑定插入失败，前面两步却不会自动撤销。

原记录中的四人同秒测试正是这样：两人成功、两人失败，八件装备都变为 IN_USE，实际只有四条绑定。这个现场说明唯一约束只是最后一道防线，它无法替代完整的事务设计。

同时，装备领用原来采用“先查询状态，再无条件更新”。两个请求可能都先查到 IN_STOCK，随后都把同一件装备改成 IN_USE。即使编号不冲突，也仍然存在重复领用窗口。

因此需要分别回答三个问题：编号怎样全局唯一？多步写入怎样一起失败？共享装备怎样只让一个请求领用成功？

编号要依赖数据库身份，不要依赖时钟和局部序号

修复后的绑定编号为：

打卡记录先插入数据库并取得主键，再用“记录 ID + 装备 ID”区分绑定。这样，不同签到请求天然使用不同记录 ID，不再共享同一秒内从 1 开始的序号空间。

这个方案还有几个实际好处：

  • 不需要引入额外随机数或分布式发号器；
  • 不受服务器时钟精度和时钟回拨影响；
  • 从编号可以直接看出所属打卡记录和装备，排查更方便；
  • 保留原唯一约束，历史编号也不需要重写。

字段长度同样经过边界核对。两个正 BIGINT 最大值各有 19 位，加上开头的 B 和中间的连字符，总长恰好为 1 + 19 + 1 + 19 = 40，不会超出现有 VARCHAR(40)。这里依赖的是数据库主键和装备 ID 的身份语义，而不是“通常 ID 很短”的经验假设。

唯一性设计应该先问“业务上哪两个身份确定一条记录”，再决定格式。把时间字符串当作并发发号方案，往往只是把冲突藏到了更细的时间粒度里。

事务覆盖整次签到，失败才不会留下半成品

签到入口增加：

现在，打卡记录、装备状态和绑定写入处于同一事务中。第二条绑定失败时，第一条绑定、装备状态和打卡记录都要一起回滚，而不是只让调用方收到一个异常。

rollbackFor = Exception.class 明确了回滚范围，但真正保证一致性的不是注解本身，而是它覆盖了整个写入单元。若只在绑定方法上加事务、或者让异常被内部吞掉，仍然可能留下部分成功。此次修复把事务放在 Service 的公开签到入口，和实际调用链一致。

事务也让“失败后的重试”变得可验证：故障移除后，同一个账号、同一个合法请求应能重新签到，而不是被上一次失败留下的“在岗”状态或“已领用”装备挡住。

先查状态只能用于提示，条件更新才负责竞争

装备查询和业务校验仍然保留，它们可以尽早发现不存在、维修、禁用、非通讯类等非法输入。但并发安全的最后判断必须落在数据库写入上。

对应的语义是：只有更新瞬间仍在库且未禁用的装备，才能从 IN_STOCK 变为 IN_USE。两个请求竞争同一件装备时，数据库行锁会把两次更新串行化；后到的请求再评估条件时，状态已经改变，影响行数为 0，于是抛出业务异常并回滚整次签到。

按装备 ID 排序则让重叠装备集合使用一致的加锁顺序，降低交叉更新形成死锁的风险。它是风险削减，不是“永不死锁”的承诺；数据库超时、其他写入路径和锁等待仍需在目标环境观察。

自动回归不仅测“成功”，也要制造中途失败

这次补充了 5 个回归用例，使用 H2、真实 Spring 事务和 MyBatis SQL，覆盖：

  1. 四人同秒并发时绑定编号不重复；
  2. 第二条绑定写入失败时，记录、装备和第一条绑定整体回滚；
  3. 并发竞争共享装备时仅一人成功；
  4. 校验之后被禁用的装备不能继续领用；
  5. 最大 BIGINT ID 组合不会超过编号字段长度。

第二项尤其重要。普通成功测试无法证明事务边界正确，必须在“已经写入一部分”的位置制造故障，再检查所有相关表和状态。第四项则专门覆盖查询校验与条件更新之间的时间窗口，防止实现退回到只依赖事前校验。

H2 用例适合快速回归，但不能替代目标数据库验证。因此后续又在真实 Spring Boot、KingbaseES、Redis 链路上执行了接口级回归，而不是只停留在单元测试环境。

真实链路验证：成功、失败、恢复都要检查

原记录中的真实环境回归共执行 107 次 HTTP 请求、260 个检查点，全部通过。与这次缺陷最相关的结果包括：

场景 观察结果
四人同秒签到 数据库确认四条签到同秒发生，4/4 成功，八条绑定编号全部不同
第二条绑定真实写入失败 对专用测试装备临时增加 CHECK 约束；打卡记录和绑定均为 0，两件装备恢复在库
故障移除后的重试 原账号、原请求签到成功，后续离岗与归还正常
两人竞争共享装备 恰好一人成功；失败方无记录和绑定残留，独有装备仍在库
完整离岗链路 在岗回查、离岗、解绑和归还通过，成功测试数据无 IN_USE 残留
非法与边界输入 空装备、数量不足、重复 ID、禁用、维修、非通讯、已领用等被拒绝

同秒四个签到请求在该轮本机小并发观测中约 42～50 ms。这只能说明当时四个请求的接口观测，不是两万人容量结果，也不是生产 P95。

验证还没有覆盖手机摄像头、真实定位采集、自动离岗和两万人打卡。把这些未覆盖项写出来，才能避免“接口一致性回归通过”被误读成“整个业务与容量全部验收通过”。

修复代码不会自动修复历史脏数据

新实现保证的是后续请求的一致性，不会自动找出并修复此前已经残留的打卡记录、装备状态和绑定。历史数据如果经历过旧版本失败，应按批次单独核对：

  • 没有有效绑定却仍在岗的记录；
  • 显示 IN_USE 但没有对应有效绑定的装备；
  • 已离岗记录对应的未解绑绑定；
  • 同一装备存在互相矛盾的有效占用关系。

清理或补偿前应保留证据并确认业务口径，不能只删其中一张表，否则可能制造新的不一致。此次回归也使用独立前缀数据，没有自动删除原有业务记录。

可复用的并发写入检查清单

这类多步写入可以按四个问题审查：

  1. 唯一性：业务编号是否由全局身份确定？唯一约束冲突时会发生什么？
  2. 原子性：所有相关写入是否在同一事务内？中途异常是否真的向外传播并回滚？
  3. 竞争性：共享状态的最后判断是否仍在“先查后改”？条件更新失败是否被检查？
  4. 可验证性：是否有中途失败、共享资源竞争和故障后重试的测试，而不只有正常成功路径？

这次修复的关键不是某一行代码更巧妙，而是三层防线终于指向同一个结果：要么签到记录、装备状态、绑定全部成功，要么什么都不留下。
