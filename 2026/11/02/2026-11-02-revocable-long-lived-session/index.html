长效登录不是改长 JWT：Cookie、Redis 与撤销的一致性设计

发表于 2026-11-02 分类于 工程实践

展示页面长时间不操作，刷新后却回到登录页。只把 JWT 有效期改长通常不够，因为 Cookie 和 Redis 会话可能更早过期；更难的是，长效会话仍必须支持主动退出、强制下线和配置关闭后的立即撤销。

🎧 文章导读

需求不是“永久 Token”，而是可控制的长会话

这次只给指定展示账号开启长效登录，其他账号继续使用原规则。账号管理页面提供开关，配置保存到数据库，不使用额外白名单；默认长期有效期为 10 年，由网关配置控制，不在页面暴露。

行为定义里有几条很容易漏掉：

  • 开启开关只对下一次登录生效，当前普通会话不会自动变长。
  • 关闭开关要撤销该账号现有全部长效会话。
  • 主动退出和强制下线仍然有效。
  • 旧客户端不传开关字段时，保留数据库原值，不能意外关闭或撤销。
  • 沿用原编辑用户权限，不新增权限点。

因此，目标不是让 Token 永远有效，而是让一类账号获得可配置、可撤销、与普通账号隔离的长会话。

三处有效期必须一起考虑

现有登录状态同时依赖 JWT、浏览器 Cookie 和 Redis 登录缓存。任何一处先过期，另外两处再长也没有用。


图 1：长效登录是三段协作，不是一次 JWT 参数修改。

账号侧新增 long_lived_login 字段，默认 '0'。登录响应把账号配置传给网关；网关仅对明确开启且用户 ID 有效的账号重签长效 JWT，延长相关会话 TTL，并返回 tokenExpiresIn；前端使用该秒数设置 Cookie 有效期。普通账号没有返回值时，继续使用原默认 Cookie 行为。

数据库改动也不能只加实体和查询映射。审查中曾发现“页面保存成功但数据库没更新”的风险：动态 SQL 的 updateSelective 没有同步加入新字段。后续通过真实 MyBatis BoundSql 测试覆盖 '0'→'1'、'1'→'0'、null 保留原值和新增字段，避免 Mock 验证漏掉实际更新语句。

登录时延长，还可能被后续续期缩回去

长效 JWT 带有专门的用户标识，并保留登录序列。网关在登录成功后维护 Token、Token 索引和登录序列之间的映射，同时删除原普通 Token 的缓存映射，避免同一次登录留下普通与长效两个有效入口。

更隐蔽的问题发生在后续请求：框架的自动续期可能按普通会话配置重新设置 Redis TTL，把登录时刚延长的有效期缩回去。

为此，长效会话过滤器识别对应请求，在请求完成后恢复登录序列、Token 和索引的长期 TTL。普通 Token 不进入这段逻辑。如果登录序列已经不存在，说明会话已退出或被强制下线，过滤器不再续期，并清理残留 Token 与索引。

主动退出也不能只依赖框架默认清理。登出入口额外执行长会话退出，显式删除登录序列、实际 Token 和 Token 索引，避免旧 Token 在退出后仍能重放。

关闭开关，难在事务与并发

撤销操作放在数据库事务成功提交之后。否则数据库一旦回滚，就会出现“配置仍开启，但会话已经删掉”的不一致。

但只调整时机还不够。考虑这个竞态：某个登录请求在关闭前已经读到旧账号快照，等数据库关闭提交后才进入网关签发长会话。如果没有额外防线，它可能把刚清掉的长会话重新写回来。

本次设计使用禁用标记堵住这条路径：


图 2：先禁止新长会话，再清存量；鉴权前复验用于兜住清理遗漏。

  1. 数据库关闭事务提交后，先写入该用户的禁用标记。
  2. 再清理现有长会话；网关签发长 Token 前复验标记，旧快照登录只能保持普通会话。
  3. 长效请求进入后续鉴权链之前也检查标记，发现禁用便统一返回 401，不再进入下游或续期。
  4. 重新开启时，在事务提交后删除禁用标记；旧 Token 不恢复，必须重新登录。

最后一道鉴权前检查很重要：即使 Redis 清理异常遗漏，旧长效 Token 也不能继续使用。

多会话撤销，不能依赖一个看似方便的批量 API

同一账号可能在多处登录，只清当前 Token 不够。最初的框架批量缓存方法还存在两个实现问题：按键模式获取时可能漏键；读取带前缀的完整键时又重复拼接前缀，导致实际取不到目标值。

最终方案改为完整枚举实际键，并用 SCAN 代替阻塞式 KEYS。每批提示数量为 256，扫描结果先放入 HashSet 去重，关闭游标后再删除，避免边扫描边改变键空间。

撤销只扫描目标用户的会话键模式，同时处理 Token 索引和登录序列。即使索引已经缺失，也仍能删除残留登录序列；其他账号的键不匹配，不应被清理。

这里也有一个值得推广的审查方法：不要只看方法名像不像“批量删除”，要沿真实框架实现确认键是否完整、前缀是否一致、遍历是否可靠。

验证结果与上线边界

原笔记记录的最新代码验证为：admin 71 项、gateway 13 项、前端相关 7 项测试通过，改动文件 ESLint 和前端生产构建通过。多会话测试使用真实缓存服务配合内存模拟的底层 Redis，尚未完成真实 Redis、数据库和浏览器联调。

前端全量测试当时另有 1 个未改动模块失败，原因是测试中的 $store 未初始化；全量 lint 也有其他未改动页面的既有格式问题。目标测试通过不等于全仓检查全绿。

真实环境验收至少要覆盖：普通账号行为不变；开启后重新登录才获得长会话；关闭后所有登录位置返回 401；重新开启不复活旧 Token；主动退出后旧 Token 不可用；多处登录能全部撤销且不影响其他账号。

原记录中的功能提交仍只在本地功能分支，数据库迁移、部署和浏览器联调均未执行。长效登录的核心也不是“10 年”这个数字，而是三条一致性：三处有效期一致、退出与续期一致、数据库配置与可撤销性一致。
